## الاختيار والتكلفة

Render: خدمة Web تعمل بـDocker، نسخة واحدة في Frankfurt، قرص دائم 1GB على `/data`، وحفظ SQLite داخل `/data/k92n`.
الخطة `starter` اسم مدعوم للخطة الأساسية: 512MB و0.5CPU، نحو 7 دولارات شهريًا، والقرص 0.25 دولار/GB شهريًا. التقدير الأساسي 7.25 دولار/شهر قبل الضرائب والاستهلاك الإضافي وأي رسوم حساب أخرى. المبلغ النهائي يعتمد على شاشة الطلب. هذه سعة تجربة شخصية وليست سعة إنتاج مقاسة.
مصادر: https://render.com/pricing و https://render.com/docs/blueprint-spec و https://render.com/docs/disks .

لا تستخدم الخطة المجانية لهذا الدفتر: القرص الدائم مطلوب. لا توسّع إلى أكثر من نسخة بهذا التصميم؛ قاعدة SQLite محلية لنسخة واحدة. النشر وإعادة التشغيل قد يسببان انقطاعًا، ولا يوجد ادعاء بتوافر عالٍ.

## ماذا تحتوي الحزمة؟

- `../../render.yaml`: خطة وقرص وفحص صحة ومتغير سر مولّد تلقائيًا، والنشر التلقائي معطّل.
- `infra/Dockerfile.render`: بناء .NET من المصدر، تشغيل مستخدم app غير الجذر، shell وتهيئة SSH حسب متطلبات Render، وأداة SQLite backup. لا يثبّت خادم sshd.
- `infra/render-entrypoint.sh`: يرفض غياب السر، والمنفذ غير الصالح، وغياب mount، ومسار بيانات خارج القرص، وعدم القدرة على الكتابة. لا يرجع إلى مساحة مؤقتة إذا فشل الحفظ.
- `src/` و`tests/`: المصدر والاختبارات، مع ملفات قفل NuGet؛ `tools/`: أدوات تحقق ونسخ احتياطي.
- `evidence/`: نتائج التجهيز الجديدة؛ الملفات ذات بادئة upstream دليل تاريخي من البناء السابق، وليست إثبات تشغيل Docker.
- `source-provenance.json`: ربط هذه النسخة ببصمات المصدر السابق.

## النشر من الهاتف

1. اربط حساب Render عبر التكامل المقترح في المحادثة. المستودع الحالي يحتوي الوحدة في `apps/k92n` وإعداد Render في الجذر؛ تحتاج تفويض Render لقراءة هذا المستودع. لا تضع الوحدة في الجذر، وتفويض Render لقراءته. تسجيل commit وطلب الدمج يثبت رفع المصدر فقط، وليس نشر Render.
2. في Render اختر New → Blueprint، ثم المستودع والفرع المقصود. راجع الخطة المدفوعة والقرص والمنطقة والتكلفة قبل Apply. إنشاء الخدمة يحمّل حسابك رسومًا.
3. اقرأ سجل البناء. إذا فشلت صلاحيات القرص، سيوقف المشغّل الخدمة. تحقّق من ملكية mount للمستخدم app عبر آلية المنصة الموثقة؛ لا تستخدم chmod 777، ولا تتجاوز فحص القرص، ولا تشغّل التطبيق كجذر كحل مؤقت. صلاحيات القرص **لم تُختبر على Render**.
4. بعد نجاح النشر، افتح رابط HTTPS الذي تعرضه لوحة Render. `/healthz` يجب أن يعيد status=running مع productionReady=false؛ الصفحة الرئيسية تعرض واجهة المشغّل.
5. احصل على `K92N_OPERATOR_TOKEN` من إعداد Environment بحسابك وأدخله في الواجهة. احتفظ به في مدير كلمات مرور، ولا ترسله هنا ولا تضعه في ملف أو لقطة شاشة منشورة. الواجهة تحتفظ به في الذاكرة فقط.
6. تأكّد أن طلب API بدون الرمز يُرفض بـ401، وأن `/api/integrity` بالرمز يعيد نتيجة صحيحة. استخدم قاعدة تجريبية وبيانات وهمية حتى تُغلق بوابات التحقق.
7. أضف حسابًا تجريبيًا وقيدًا متوازنًا؛ دوّن العدد وHeadHash خارج الخدمة؛ أعد تشغيل الخدمة، ثم تأكد من بقاء العدد والبصمة. كرّر بعد نشر جديد. نجاح mount وحده لا يثبت بقاء البيانات.

فحص المصدر محليًا:

```bash
python3 tools/test_hosting.py
python3 -m unittest discover -s tests -p 'test_*.py'
dotnet build src/K92N.Host/K92N.Host.csproj -c Release
dotnet run --project tests/K92N.Tests/K92N.Tests.csproj -c Release
```

اختبارات hosting تستبدل mountpoint وdotnet ببرنامجين اختباريين لفحص منطق التشغيل. لا تثبت تركيب قرص أو تشغيل حاوية حقيقية.

## BalauDeck — بعد أن تظهر الخدمة

خدمة Render المدفوعة تدعم SSH. من إعداد حساب Render أضف **المفتاح العام فقط**. احتفظ بالمفتاح الخاص على جهازك؛ استخدم إنشاء/استيراد المفتاح في عميلك إن كان متاحًا، ولا تشاركه في الدردشة.
ثم داخل الخدمة: Connect → SSH. خذ القيم من الأمر الفعلي الذي تعرضه المنصة.

| حقل BalauDeck / New SSH | القيمة |
|---|---|
| الاسم | BLACKWOLF K92N |
| Host | اسم المضيف في أمر SSH الذي يعرضه Render |
| Port | المنفذ المعروض؛ عادة 22 |
| Username | اسم المستخدم المعروض قبل @؛ لا تفترض root أو app |
| Authentication | المفتاح الخاص المقابل للمفتاح العام المضاف لحساب Render |

تحقق من بصمة المضيف عبر قناة موثوقة قبل اعتمادها. SSH هنا جلسة داخل حاوية الخدمة، وليس VPS كاملًا؛ تُغلق عند إعادة النشر. لا تحتاج New Database في BalauDeck لأن المحرك الحالي SQLite، وليس MySQL/MariaDB. دعم SFTP يعتمد على العميل والمنصة ولا يُعد مختبرًا هنا.
المصدر: https://render.com/docs/ssh .

## النسخ الاحتياطي والاستعادة

داخل جلسة SSH، بعد التأكد من المصدر والمسار:

```bash
mkdir -p /data/backups
python3 /app/tools/backup.py backup /data/k92n/k92n-local.db /data/backups/k92n-2026-11-08.db
```

استخدم اسمًا جديدًا لكل نسخة؛ الأداة لا تستبدل ملفًا موجودًا. نزّل النسخة خارج قرص الخدمة عبر قناة نقل آمنة تدعمها المنصة. النسخة على القرص نفسه ليست حماية من فقدان القرص. لا تنسخ ملف SQLite الرئيسي وحده أثناء الكتابة لأن WAL قد يحتوي عمليات معتمدة. الأداة تستخدم SQLite backup API؛ لا تشفّر الملف المنزّل، فاحفظه مشفّرًا خارج الخدمة.

`restore-new` يكتب ملفًا جديدًا فقط؛ لا يستبدل الدفتر الحي. تمرين الاستعادة يجب أن يكون على بيئة مستقلة، مع فحص النزاهة ومقارنة مرجع خارجي للعدد والبصمة قبل اعتماد أي استبدال. لا تستخدم snapshot عامًّا للقرص كبديل لنسخة قاعدة متسقة.

## بوابات ما زالت مفتوحة

Docker build/run، نشر Render، ملكية القرص، بقاء البيانات بعد restart/redeploy، HTTPS وSSH الفعليان، الاستعادة الخارجية، وتجربة iPhone: **NOT_RUN**.
لا توجد OIDC/RBAC متعددة المستخدمين أو عزل tenants لهذا المضيف؛ الرمز سلطة مشغّل واحدة. لا تفتح الخدمة لعملاء متعددين، ولا تنقل بيانات محل حقيقية قبل مراجعة الأمان والاستعادة. السر ليس بديلًا عن نظام صلاحيات إنتاجي.
قواعد جديدة فقط؛ لا ترحيل تلقائي لقاعدة قديمة. مشروع FINANCE P0 PostgreSQL مستقل ولم يُستبدل بهذه الحزمة.

## الخطوة اللازمة لإنشاء الخدمة

ربط Render، تحديد مستودع المصدر، وموافقة التكلفة المعروضة. بعد ذلك يمكن إنشاء خدمة محددة والتحقق منها وتزويدك برابط HTTPS وحقول SSH الفعلية. لا يوجد شراء أو نشر ضمن عبارة «التجهيز» هذه.
